# プロジェクト設計方針（test10.mq5 トレード EA）
# 1. 基本設計方針
- このコードはMT5（MQL）でエキスパートアドバイザー（EA）として動作する。
  - コードは全てMQL5で記述すること。
  - 構文チェックやエラーチェック等も全てMQL5に準拠すること。
- 本EAは H1で環境認識、M15で補助シグナル、M1で執行判断 を行うマルチタイムフレームEAとする。
- H1/M15は「状態判定・シグナル生成」、M1は「執行条件の最終判定と価格管理」を行う。
- OnTimer() は事前計算専用、OnTick() は執行専用 を原則とする。
- 「価格変数」と「実行可否フラグ」は分離する。  
  - 「価格が入っていること」と「その価格を使って発注/決済してよいこと」は別概念として扱う。
- フラグは ON = 実行可 / 有効、OFF = 実行不可 / 無効 で統一し、禁止フラグは使わない。
  - ただし、失敗時に実行するものに関しては、失敗フラグを使うことは許容する。
- 状態判定、シグナル、指標値等は H1/M15/M1 の 足確定ベース、M1の執行は ティックベース を基本とする。

# 2. アーキテクチャ
## 2-1. マルチタイムフレーム構成
- H1（1時間足）
  - 市場環境判定
  - トレンド/レンジ判定
  - トレンド方向判定
  - トレンド強弱判定
  - トレンド継続性/移行状態判定
- M15（15分足）
  - RSI / MACD / ダイバージェンス / MACDクロスの検出
  - 過熱感・逆行警戒・追撃禁止/弱化などの補助フラグ生成
  - 補助シグナル判定
  - M1に渡す「次足限定の補助情報」を生成
- M1（1分足）
  - 発注価格・決済価格の算出
  - 発注トリガー/決済トリガーの管理
  - ST / BB / Stochastic / ATR を用いた最終執行判断
  - OnTickでの発注・決済実行
- 閾値や判定の基準値は全てinput変数にはせず「内部パラメータ」として指定する。
- 各指標値は毎回すべてを計算する。使用するかどうかはその後に判断する。
- 各指標値は直近3本の確定足を取得する。ただし、ダイバージェンス判定に関してはその限りではない。

## 2-2. イベント処理の責務
### 2-2-1. OnTimer()
- 毎秒実行し、各時間足の「新規確定足ができたか」を確認する。足が未確定なら指標の判定処理はスキップする。
- H1/M15/M1ごとに新規確定足ができていた場合は各々の処理を行う。なお、各処理は`CTrend`関数群にまとめる。
- CTrend関数群は、各時間足の指標計算・判定・フラグ更新を行う。
  - 指標値は取得に失敗した場合はその場で1回までリトライする。
  - リトライしても取得に失敗した場合は取得フラグをfalseにして、次回のOnTimer（1秒後）で再取得する。

### 2-2-2. OnTick()
- 発注・決済を行う。
- OnTimerで事前計算済みの変数を参照して執行する：
  - 各種 entry/close 指標値
  - 各種 entry/close 実行フラグ
  - 閾値通過フラグ
  - M15シグナル消費状態
- OnTick内で新たにH1/M15の指標計算や重い判定は行わない。

### 2-2-3. OnTrade()、OnTradeTransaction()
- 発注・決済の結果を受けて、ポジションの保有数をカウントする。

# 3. H1（環境認識）の設計
## 3-1. 使用指標・計算値
- ADX
- DI+ / DI-
- EMA短期 / EMA長期
- DI差（`abs(DI+ - DI-)`）

## 3-2. H1の役割
- H1は以下を担当する。
  - トレンド/レンジ/不明の環境判定
  - トレンドの上昇/下降方向判定
  - 強トレンド/弱トレンド判定
  - トレンド継続性/移行状態判定

## 3-3. 判定の分類
### 3-3-1. 環境判定の分類
- 環境（相場）認識：`enum TrendType`で管理する。
  - TREND_STRONG_UP
    ADX >= 40 かつ DI+ > DI- かつ EMA短期 > EMA長期
  - TREND_WEAK_UP
    ADX >= 25 かつ DI+ > DI-
  - TREND_STRONG_DOWN
    ADX >= 40 かつ DI+ < DI- かつ EMA短期 < EMA長期
  - TREND_WEAK_DOWN
    ADX >= 25 かつ DI+ < DI-
  - TREND_RANGE
    ADX < 18
  - TREND_UNKNOWN
    上記以外
- 強トレンドはADXの値だけで判定するのではなく、方向性の整合性（DIとEMAの一致）も確認する。
- ADXのみが高い場合は「強いモメンタム候補」として扱うが、方向確定の最終判定ではDI/EMAの一致を重視する。

#### 3-3-1-1. 方向判定の優先順位
- DI方向を主判定、EMA方向は補助判定とする。
- DIとEMAが不一致でも、通常トレンド判定ではDI方向を優先する。
  - ただし、強トレンド状態および追撃可否の判断ではDIとEMAの一致を必須要件とする。
- ADXが高いだけの場合でも、方向の信頼度を上げるためにDI/EMAの整合性を確認する。

#### 3-3-1-2. DI差の扱い
- DI差が一定値未満のときは、方向の信頼度が低いとみなす。
- 環境判定時の方向性採用条件として DI差閾値を使用する。
- 継続性判定（加速/減速/維持等）は毎回行うが、環境がトレンド判定ではない場合は継続性を売買ロジックに採用しない。

### 3-3-2. 継続性判定の分類
- トレンドの継続性：`enum TrendState`で管理する。
  - TREND_ACCELERATE
    25 <= [3] < [2] < [1]
  - TREND_DECELERATE
    [3] > [2] > [1] >= 25
  - TREND_REACCELERATE
    [3] > [2] < [1] かつ 25 <= [3] < [1]
  - TREND_RECOVERY_MAINTAIN
    [3] > [2] < [1] かつ [3] >= [1] >= 25
  - TREND_STALL_MAINTAIN
    [3] < [2] > [1] かつ 25 <= [3] ≒ [1]
  - TREND_MAINTAIN
    [3] ≒ [2] ≒ [1] >= 25
  - RANGE_MAINTAIN
    [3] ≒ [2] ≒ [1] < 18
  - RANGE_TO_TREND
    [3] ≒ [2] < 25 かつ 25 <= [1]
  - TREND_TO_RANGE
    18 <= [3] ≒ [2] かつ [1] < 18
  - STATE_UNKNOWN
    上記全てを満たさない場合
- 直近3本の確定済みADX値（[3][2][1]）で判定する。
  - 比較対象は全てH1確定足
※「≒」は必ずしも近似値ではないが、その全てが同じ条件であることを示す。
  例えばTrend_Maintainは[3][2][1]の全てが25以上であれば、それぞれが大きく乖離していても維持判定とする。
  ただし、Trend_Accelerate等の条件を満たす場合はそちらを優先する。

#### 3-3-2-1. 継続性判定の補足
- 直近確定足（[1]）が「18 ≦ ADX < 25」のグレーゾーンの場合（グレーゾーン滞在中）は「相場移行」とはみなさない。
  - ただし、グレーゾーンを長く経由した後に 18 未満または 25 以上へ到達した場合は、その到達時点で移行判定とする。
    - 例：「20→19→21→22→20→18」：最後に18未満へ入った時点でレンジ移行（TREND_TO_RANGE）判定
    - 例：「20→22→24→26」：最後に25以上へ入った時点でトレンド移行（RANGE_TO_TREND）判定
- つまり、「グレーを飛び越えたかどうか」ではなく、「最終的に判定ゾーンへ到達したか」を見る。

# 4. M15（補助シグナル）の設計
## 4-1. 使用指標
- RSI
- MACD（メイン、シグナル、ヒストグラム）
- MACDクロス
- RSIダイバージェンス
- MACDダイバージェンス

## 4-2. M15の役割
- M15はH1環境に対する補助シグナルを生成し、M1執行の補強または抑制に使う。
- 指標は相場状況（レンジ/トレンド相場）によって、RSI、MACDを使い分けるが、両方の指標を常に計算しておく。
  - 「不要な方の値を計算しない」のではなく、両方計算し、採用ルールを環境ごとに分ける。

## 4-3. 判定の分類
### 4-3-1. 過熱警戒の分類
- 相場の過熱感：`enum OverheatType`で管理する。
  - OVERHEAT_OVERBOUGHT
    RSI > 70
  - OVERHEAT_OVERSOLD
    RSI < 30
  - OVERHEAT_NONE
    上記全てを満たさない場合

### 4-3-2. 逆行警戒の分類
- ダイバージェンス判定用：`enum DivergenceType`で管理する。
  - DIVERGENCE_BULLISH
    強気（ブル）ダイバージェンス （価格が下降/指標が上昇）
  - DIVERGENCE_BEARISH
    弱気（ベア）ダイバージェンス （価格が上昇/指標が下降）
  - DIVERGENCE_CONFLICT
    強気・弱気両方同時発生
  - DIVERGENCE_NONE
    ダイバージェンスなし
- ダイバージェンスは各指標（RSI、MACD）毎に算出する。
- ダイバージェンスは判定専用関数を用いて計算する。

## 4-4. 各環境ごとの判定基準
### 4-4-1. トレンド相場時の判定基準
#### 4-4-1-1. トレンド相場で主に使うもの
- MACDヒストグラム
- MACDクロス
- MACDダイバージェンス
- RSIは「逆行警戒・過熱警戒」の補助として扱う

#### 4-4-1-2. トレンド時の MACD の扱い
- MQL5の`iMACD`ハンドルから取得できるのは通常以下の2つである。
  - MACDメイン
  - MACDシグナル
- MACDヒストグラムは原則として`main - signal`で自前計算する。
- MACDクロスは「MACDメインとMACDシグナルのクロス」を指す。
  - 上抜け：強気寄り
  - 下抜け：弱気寄り
- トレンド時の使い方
  順張り方向の補強
  逆行クロス時の追撃禁止/決済警戒
  M1のトレンド決済補助（必要なら採用）
- M15のMACDクロスは単独でエントリ確定に使わない。
  あくまでM1執行の補強または抑制フラグとして使う。

### 4-4-3. トレンド時のRSIの扱い
- RSIの 70/30 到達そのものを逆張りシグナルとして使わない。
  トレンド中はRSIが70以上/30以下に張り付くことがあり得るため、RSI値そのものを売買方向反転の根拠にしない。
  - ただし、以下のような状況では警戒フラグとして使うことは認める。
    上昇トレンド中に RSI が高止まり後に失速
    下降トレンド中に RSI が低止まり後に反発
    RSIダイバージェンスが出現
  - 警戒フラグが立った場合は、EA内で以下のように具体的に作用させる：
    新規追撃を禁止する
    ロット増加を禁止する
    決済側の条件を緩める（早めに逃がす）
- RSI閾値について
  - 現時点ではレンジ相場とトレンド相場の両方で同じ70/30閾値を使う。
  - ただし、将来的には「レンジ用」「トレンド用」で別設定できる設計余地を残す。

## 4-4-2. レンジ相場時の判定基準
### 4-4-2-1. レンジ相場で主に使うもの
- RSI
- RSIダイバージェンス
- MACD系は補助情報として取得してもよいが、主判定にはしない

## 4-4-2-2. レンジ時のRSIの役割
- 過熱感の確認
- 逆張り方向の妥当性確認
- M1のBB逆張りエントリのフィルタ

## 4-5. ダイバージェンスの扱い
### 4-5-1. 基本方針
- 価格の推移と指標の推移の逆行を確認する。
- 15MのRSI、MACDで判定する。
- 状況・条件に関わらず、毎回対象の全ての指標でダイバージェンスを確認する。
- 確認後にその結果を利用する/しないを判断する。

### 4-5-2. ダイバージェンスの判定ロジック
- 価格値・指標値の直近の14足を確認し、その中から価格・指標の高値/安値のピークを3つ検出する。
  - ピークは高い/低い順に3つを検出する。
    - 価格高値が上昇し、指標高値が下降する場合は弱気ダイバージェンスと判断する。
  - 価格安値が下降し、指標安値が上昇する場合は強気ダイバージェンスと判断する。
  - 同一期間内に強気・弱気の両方が検出された場合は、`DIVERGENCE_CONFLICT` とする。
  - 判定にはピーク検出の窓幅と最小間隔を設け、偽シグナルを減らす。
- レンジ相場
  RSIダイバージェンスを主に採用
  MACDダイバージェンスは参考情報または補助
- トレンド相場
  MACDダイバージェンスを主に採用
  RSIダイバージェンスは「逆行警戒」寄りの補助情報

## 4-7. シグナルの寿命
### 4-7-1. 基本方針
- M15のダイバージェンス/クロス/警戒フラグ等は、永続シグナルとして使わない。
  原則として「次のM1足のみ有効」または「最初のM1エントリ/決済判定で消費」 とする。
  実装上は pendingNextM1 と usedForEntry / usedForClose で管理する。
  15分間ずっと効かせ続けない。

### 4-7-2. M15シグナルの寿命管理
- M15で発生したシグナルは、以下のように扱う。
  pendingNextM1 = true
    次のM1足で有効
  M1側で参照したら、用途に応じて usedForEntry / usedForClose を更新
  使用後は再利用しない

## 5. M1（執行）の設計
### 5-1. M1の役割
- M1は以下を担当する：
  - 発注価格・決済価格の算出
  - 閾値通過フラグ管理
  - ブレイク/リトレース状態管理
  - 実際の発注・決済執行
### 5-2. 使用指標
- SuperTrend
- Bollinger Bands
- Stochastic
- ATR

## 6. M1の売買方針（大枠）
### 6-1. レンジ相場
- 発注：BB中心
- 決済：BB + Stochastic
- M15のRSI系シグナルでフィルタ/補強
### 6-2. トレンド相場
- 発注：SuperTrend中心
- 決済：SuperTrend + Stochastic
- 必要に応じて M15 MACDクロス / ダイバージェンスで補助
- 強トレンド時のみ追撃許可

## 7. M1レンジ戦略
### 7-1. 発注
- レンジ時の発注は BB 2σ への接触を起点にする。
- ただし、接触した瞬間に即成行するのではなく、接触後の戻りを見てエントリするブレイクアウト後リトレース型で管理する。
- 基本フロー
  - 価格がBB上限/下限に接触または超過
  - g_entryThresholdCrossedBuy/Sell をON
  - その後、価格が所定の戻り位置へ戻ったらエントリ
- 補足
  - レンジ戦略では、「2σ到達 → 反転確認」型を採用する。
  - したがって、BB接触は即発注条件ではなく、発注準備フラグON条件として使う。
### 7-2. 決済
- レンジ決済は BB逆側到達 + Stochastic を基本とする。
- ただし、BBに1度触れた瞬間で即決済するか、いったん抜けて戻った時に決済するかは、実装パラメータで切替できる余地を残す。
- 本件の「調整可能」は「EAの設定パラメータまたは関数モードとして選択できる」ことを指し、
  市場を自動判別して曖昧に切り替えることではない。
- 現時点の優先方針は以下：
  - 基本は「逆側帯到達で決済候補」
  - Stochasticでタイミング確認
  - 「帯に触れた瞬間決済」か「戻り確認後決済」かは関数分離して後で調整可能にする
- もしレンジでエントリーを確定した後にM1/環境がトレンドへ移行した場合は、
  既存のレンジエントリー条件を単純に破棄せず、当該エントリーは引き続き保持する。
  ただし、トレンド優勢になったタイミングでは追加のトレンド決済条件（SuperTrend割れ等）を別途評価する。

## 8. M1トレンド戦略
### 8-1. 初撃
- トレンド時の初撃は、SuperTrend反転 / STクロス型を基本とする。
- 初撃は「押し目」ではなく、環境確定後の方向転換検出またはレンジ→トレンド移行直後の初動捕捉を想定する。
### 8-2. 追撃
- 追撃は押し目/戻りを取る。
- 強トレンド時のみ許可する。
- 追撃時は以下を必須条件とする：
  - H1が強トレンド
  - DI方向とEMA方向が一致
  - M15逆行シグナルなし
  - 前回追撃からM1確定足3本以上経過
### 8-3. 押し目/戻りの基本定義
- 上昇トレンドの例：
  - 価格 > ST
  - 価格がSTへ近づく
  - 再びSTから離れる
- これを押し目候補とみなす。
- 現時点の実装方針
  - 押し目判定は固定バッファを使う方針とする（ATR連動ではなく、まず固定値で実装）。
  - 例：
    - pullbackBuffer：STへ近づいたとみなす距離
    - entryBuffer：再上昇を確認する距離
  - 例（上昇トレンド）
    - Close[1] <= ST + pullbackBuffer で押し目接近判定
    - Close[0] > ST + entryBuffer で再上昇判定
  - pullbackBuffer > entryBuffer を前提とする

## 9. SuperTrendの扱い
### 9-1. 重要
- `g_superTrend` / `g_superTrendDir` はM1の SuperTrend 価格と方向を保持するグローバル配列である。
  - `g_superTrend[0]` は最新1分足の SuperTrend 価格
  - `g_superTrendDir[0] > 0` は上向き、`g_superTrendDir[0] < 0` は下向き
  - `g_superTrendDir[0] == 0` は未定義/無効状態を表す
- トレンド戦略の中核指標であるため、算出ロジックを最優先で整備する。
- もし `g_superTrend` が正しく更新されていない場合は、M1トレンドエントリ/決済ロジックは代替手段にフォールバックするか、トレンド戦略を無効化できるようにする。
### 9-2. ST反転の意味
- 「価格がSTラインを跨いだこと」と「STの表示位置（価格の上側/下側）が切り替わったこと」は密接に関係するが、内部状態としては区別して扱うことを推奨する。
- EAではST反転を“フラグ化したイベント”として扱う。
- 基本方針
  - H1/M15のような大きな環境認識ではなく、M1執行イベントとして扱う。
  - ST反転を検知したら、M1側の初撃可否・決済可否フラグに変換する。
### 9-3. ST判定とティック/確定足
- STの基準値自体はM1確定足で更新する。
- その上で、OnTickではティック価格と直近確定済みST値を比較して執行する。
- つまり：
  - ST値の計算は足確定ベース
  - STを割った/超えたかの執行判定はティックベース

## 10. トレンド決済
### 10-1. 基本方針
- トレンド時の決済は以下の優先順位で扱う。
  - ブローカー側のSL（固定SL / トレールSL）
  - EA側のST割れ決済
  - Stochasticによるタイミング補助
  - 必要に応じてM15 MACD逆行シグナル
### 10-2. ST割れ決済
- EA側では、ティック価格が直近確定ST値を割ったら決済候補とする。
- ただし、常に即決済するのではなく、利益状態かどうか、M15警戒フラグの有無等で扱いを変える余地を残す。
- 現時点の方針
  - 利益確定局面では、ST割れで即決済寄り
  - 建値付近や含み損時は、固定SL / トレールSLが先に働く前提で、EA側の即時ST決済をどこまで使うかは関数分離して調整可能にする

## 11. ATRの扱い
### 11-1. M1 ATR の役割
- ATRは以下に使う：
  - ボラティリティ監視
  - ST補助
  - 急変直後の取引抑制フィルタ
  - 将来的な動的バッファ/SL調整の拡張余地
### 11-2. 急変時の扱い
- M1 ATR は「急変を完全に事前回避するもの」ではない。
- 主用途は急変後にボラが異常拡大している状態を検出し、落ち着くまで新規取引を抑制すること。
- フラッシュクラッシュ（短時間での急変（暴落、高騰⇒反落））や流動性枯渇を防ぐ万能策ではない。

## 12. 価格変数とフラグ変数の分離
### 12-1. 基本方針
- g_entryPriceBuy のような価格変数と、g_canEntryBuy のような実行可否フラグは分離する。
- ルール
  - 価格は価格として保持する
  - 発注/決済してよいかはフラグで判断する
  - 0/null を使って「価格がない」ことと「取引禁止」を兼用しない
### 12-2. 閾値通過フラグ
- ブレイク後リトレース用に、以下のようなフラグを持つ：
  - g_entryThresholdCrossedBuy
  - g_entryThresholdCrossedSell
  - g_closeThresholdCrossedBuy
  - g_closeThresholdCrossedSell
- 役割：
  - 価格が一度閾値を超えたことを記録し、
  - その後の戻りで発注/決済を行う

## 13. ポジション管理
### 13-1. 基本方針
- 同一方向は通常1ポジションまで
- 強トレンド時のみ追撃許可
- 両建ては許可する
- ただし、同一方向の連続発注は制限する
### 13-2. ロット方針
- 現時点の基準ロット方針：
  - トレンド時：基準値 × 1.0
  - レンジ時：基準値 × 0.7
  - 追撃時：基準値 × 0.5
- 現時点の優先方針は、「環境別ロット倍率 + 追撃倍率」方式で整理すること。
### 13-3. 追撃制限
- 強トレンド時のみ追撃可
- DI方向とEMA方向が一致していること
- M15逆行シグナルが出ていないこと
- 前回同方向追撃から M1確定足3本以上経過していること
- 判定方法
  - 「前回追撃時刻」または「前回追撃時のM1バー時刻」を保存し、
  - そこから M1の確定足が3本以上進んだか で判定する

## 14. 決済時の全決済方針
### 14-1. 基本方針
- EAの決済シグナル（ST割れ等）が出た場合、同一方向ポジションは損益に関係なく原則全決済する。
- 一部だけ残す、利益側だけ閉じる等の複雑な分離決済は、現時点では採用しない。
### 14-2. 理由
- 同一方向ポジションを「1つの戦略束」として扱うため
- 一部残しはロジック・整合性・検証難度が大きく上がるため
- まずは全決済で設計を単純化する
- 注意
  - ブローカー側の個別SLは各ポジションに残るため、EA全決済より先にSLが刺さる可能性はある。
  - ただし、EA側の方針としては「シグナルが出たら同方向はまとめて閉じる」を基本とする。

## 15. リスク管理
### 15-1. 必須方針
- 全ポジションに必ずSLを設定する
- トレンド時はトレールSLを使用する
- EAのロジック決済よりも、ブローカー側SLの存在を最優先の保険と考える
- 発注前にスプレッドをチェックし、スプレッドが `MaxSpread` などの設定値を超える場合は新規発注を行わない
### 15-2. 長時間保有について
- 時間決済は現時点では採用しない。
- 長時間保有は「建値付近を彷徨う状態」として起こり得るが、固定SL / トレールSLがある前提で、必須の欠陥とはみなさない。
- ただし、将来的に環境exit / モメンタムexit / 時間exitを追加する余地は残す。
### 15-3. 週末・休日の扱い
- 週末や祝日前後は流動性低下とスプレッド拡大に注意する。
- 週末直前（Friday close前）の新規発注は避けるか、明示的に無効化できる設定を用意する。
- 週末のポジションは、ブローカー締め時間までに可能な限り決済する方針を採用する。
- 休日明けの急変リスクを避けるため、週末明けの最初の足は新規発注を控え、必要に応じてエントリー条件を厳しくする。

## 16. リクエスト制御とレート制限
- ReqTimes 配列で過去 REQ_CAP 件のリクエスト時刻を保持する方式は継続してよい。
- CanReq() による発注前チェックは継続する。
- ただし、今後リクエスト数が増える場合は、循環バッファ化を検討する。

## 17. グローバル変数の管理
### 17-1. 命名規則
- グローバル共有状態：g_
- ハンドル：h_
- クラスメンバー：m_
### 17-2. 主要グローバル状態
- g_TrendTypeH
- g_TrendStateH
- g_OverheatM15
- g_DivergenceM15
- g_M15Signal
- g_entryPrice*

### 17-3. 設計原則

## 18. クラス設計
### 18-1. 基本方針
- 以下の責務分離を目指す：
  - CTrend1H
    - H1環境判定
    - TrendType / TrendState / 方向性の算出
  - CTrend15
    - M15シグナル生成
    - RSI / MACD / ダイバージェンス / クロス管理
  - CTrend1M
    - M1価格算出

### 18-2. 注意
- H1/M15/M1の責務を跨いだ直接参照は最小化する
- 可能なら「結果構造体を返す」方式に寄せる
- ただし、OnTickで参照する必要がある状態はグローバル共有でも可

## 19. 足更新失敗・古い値対策
### 19-1. 基本方針
- 各時間足について、前回更新時刻がその足の周期より古すぎる場合は、その足の判定値を無効化する。
- 例：
  - H1なら前回更新が1時間以上前
  - M15なら15分以上前
  - M1なら1分以上前
- インジケータ取得で失敗した場合は再試行を行い、それでも失敗すれば当該周期の更新をスキップする。
### 19-2. 無効化の方法
- ADX等の値を0にするのではなく、「値なし / 無効」状態として扱う。
- 理由：
  - 0 は理論上あり得る実値と区別がつかなくなるため
  - 「古い正常値のまま残る」ことを防ぎつつ、「取得失敗」と「実際の0」を区別するため
- CTrendクラスでは、CopyBuffer失敗時に `false` を返し、状態更新を行わない。
- `TryCopyBufferWithRetries` のような再試行機構を使い、1回だけの一時的な取得失敗から即座に状態破棄しない。
- OnTimerでは、必要データの取得に失敗した場合はグローバル配列を初期化するか、少なくとも実行フラグを無効化して、古いデータが使われないようにする。
### 19-3. 売買制御
- H1/M15/M1の必要データが無効な場合、新規注文は行わない。
- 決済については、ブローカー側SLが常に有効である前提で、EAロジック決済をスキップしても破綻しないようにする。
- M15やM1で取得できなかったインジケータ値は、`g_M15Signal` の `pendingNextM1` をクリアするなど、次足へ持ち越さない。

## 1. H1の移行判定を、これまでの合意に合わせて修正

- ただし、**グレーを経由した後に最終的に18未満/25以上へ入ったら移行候補**
